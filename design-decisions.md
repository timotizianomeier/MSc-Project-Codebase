- [02.08.2026] v2 cluster-s2s half-duplex limitation ACCEPTED, not patched: s2s 0.2.11 mutes the mic→VAD path while response audio streams (internal `should_listen` threading Event, set on "response complete, listening re-enabled"; NO CLI/session knob — the app's `interrupt_response=True` is sent and parsed correctly but speech during playback never reaches that gate). Consequence: interrupting the robot mid-answer defers your speech until the answer finishes (it is then processed immediately — nothing is lost); interrupts while the LLM is still generating (pre-audio) DO cancel cleanly (verified 16+ times, 02.08 session). Why accepted: (1) the fix is surgery on upstream pipeline internals we don't own, with real breakage risk days before the study; (2) in sim (Mac speaker+mic, no AEC) the muting is actively protective — disabling it reproduces the 30.07 Lite echo-storm failure mode (robot barging in on itself); (3) at 1.4-2.2s turns with brief persona answers, the exposed window is small. REVISIT TRIGGER: if mid-playback barge-in proves to be a real interaction problem on the physical robot (Lite or wireless — the wireless has hardware AEC, so clean mic audio exists and only the server-side gate stands in the way), the documented exploration path is a venv patch making the should_listen clear conditional on `interrupt_response` (patch site: api/openai_realtime pipeline wiring), plus the matching upstream feature request. Half-duplex likely also applies to the HOSTED backend if Pollen deploys a recent s2s — verify empirically before citing (one session: interrupt a long answer, check whether app.log speech_started arrives during deltas or only ms after response completed).

- [31.07.2026] Study-session lifecycle via SESSION_GATE_ENABLED + participant Start button: app launches ARMED-BUT-DORMANT (greeting deferred-not-consumed, both monitor polls no-op before touching the camera, mic forwarding gated at the same record_loop point as CONTROL_MODE, context submissions rejected with a clear RPC error) until session.start fires from /participant; then loud SESSION START banner (the post-hoc analysis anchor), greeting, and a SESSION_DURATION_MINUTES timer (default 25) whose expiry logs SESSION END, closes all gates again, and has the robot speak SESSION_OVER_PROMPT via say() (persona-consistent, not canned audio). Key decisions: (1) the once-only guarantee is SERVER-side idempotence (start_study_session returns False on repeats) — the disabled button is UX, not the mechanism; (2) recording runs the WHOLE script, the START/END banners delimit the analysis window (simpler than start-stopping the recorder, and pre-session briefing audio is itself useful); (3) composes with CONTROL_MODE: button/timer/banners identical in both arms (comparable session windows), greeting and end-announcement stay suppressed in control; (4) default OFF so dev runs keep stock behavior — the gate is enabled only in the study platform's .env; (5) gate helpers live on the ConversationHandler BASE class (default open / no-op) so console gates work without knowing the backend; (6) antenna heartbeat and head trim deliberately NOT gated — the robot looks alive while dormant, it just doesn't listen or speak.
- [31.07.2026] Idle antenna heartbeat (supervisor request: body-double presence needs *some* idle motion): ANTENNA_HEARTBEAT_ENABLED (default OFF, same fail-quiet polarity as the motion-knob family; env knob, no CLI flag) queues a 1.2s AntennaHeartbeatMove every randomized 60-120s from the MovementManager's own control loop. Antennas chosen deliberately over re-enabling breathing or the idle policy: the camera lives in the HEAD, antennas don't move it — expressive liveliness with zero cost to frame stability or the freshly calibrated HEAD_PITCH_TRIM aim. The move holds the current head/body pose and animates only antennas with a sin(pi*phase)*sin(4*pi*phase) envelope (rest at both ends, no snap); trigger fires only when fully idle (no active/queued move, not listening, not breathing — busy postpones 5s without burning the slot) and runs manager-side so the cue continues during long silent work stretches and backend hiccups. SUPPRESSED in CONTROL_MODE (control robot = fully still; may be reconsidered). Randomized interval so the cue never reads as metronomic.
- [31.07.2026] Camera aiming solved as configuration, not automation: HEAD_PITCH_TRIM_DEG composes a baseline pitch offset under EVERY outgoing pose at the single set_target choke point in moves.py — resting posture, wobble, and emotes all ride the tilted baseline uniformly; 0 = code path inert. Chosen over periodic face re-localization deliberately: auto-tracking would reintroduce unprompted motion (the thing IDLE/BREATHING=off exists to prevent), destabilize detector frames, risk hunting oscillation, and be new motion code the day before freeze. Aim verification stays in the pre-session checklist (2-3 face-positive emotion polls; first EMOTION_FRAME_DUMP frame = per-participant audit record of what the camera saw at aim time). SDK pitch sign convention undocumented → calibrate once per robot (try 8, flip sign if wrong). Same-day persona edits (v2): break/Pomodoro coaching stripped (fixed session duration managed outside the robot) + no-internet honesty rule ("never pretend to search" — the 30.07 podcast confabulation fix). Both require git pull on the Pi to reach the study platform.
- [30.07.2026] "Long-input latency" root cause = s2s sentence batching, fix = stock CLI flag `--stream_batch_sentences 1`. Investigation eliminated four suspects in order: (1) thinking tokens — patch verified in place, and /v1/responses probe with reasoning effort none returned 61 tokens in 4.2s on a 1100-token input (suppression holds even on long inputs); (2) A16 prefill — measured 1099 t/s via ollama --verbose, prefill was never slow (num_batch 2048 variant probed anyway: no change — clean negative, variant e4b-batch2048 left on the node, unused); (3) server-side generation — GIN request log across all three 30.07 sessions shows worst /v1/responses duration 8.15s while the app measured 10.8-23.4s first-audio → the gap lives on the Mac AFTER the LLM answer arrived; (4) actual cause — responses_api_language_model buffers stream_batch_sentences=3 complete sentences before yielding to TTS, which then synthesizes the whole batch before first audio: long inputs elicit long ANSWERS → 3 long sentences ≈ 5s LLM stream + 7-14s TTS ≈ the observed spikes; short answers never fill the batch → the smooth 2-4s turns. Input length was a decoy variable for answer length. batch=1 → first audio after ONE sentence (~3-5s worst case); known trade-off = possible inter-sentence gaps if TTS falls behind playback (RTF ~1.4 says it won't; fallback value 2). Side benefit: smaller TTS bursts spread thermal load. CLI flag, not a venv patch — survives s2s upgrades, must simply be present in the launch command (runbook updated).
- [30.07.2026] Control condition via --control flag (config.CONTROL_MODE): sensing runs IDENTICALLY to treatment (camera, emotion+engagement polls, session recording, all logging) while the four robot output channels are gated: (1) mic forwarding in record_loop (recorder tee deliberately BEFORE the gate: control participants are recorded, just never heard by the model), (2) startup greeting, (3+4) both intervention sends replaced by counterfactual "CONTROL: would have sent ..." INFO logs that STILL call mark_intervened() so cooldown budgets match treatment and per-session would-have-intervened counts are directly comparable across conditions; plus the context page accepts+logs submissions without waking the model (identical participant procedure). Backend session stays connected-but-silent (monitors only start after allocation, 14.07 decision; VAD never hears audio → never responds). CONTROL_MODE deliberately NOT in refresh_runtime_config_from_env — a UI settings save must never flip the experimental condition mid-session; CLI flag wins over env and is set after the .env reload in run(). Loud multi-line CONTROL MODE banner at startup so a mis-launched session is caught immediately. Robot WAV never being created in control sessions doubles as an integrity check that the robot stayed silent.

- [27.07.2026] Cluster-LLM thinking latency SOLVED via request param, not template surgery. Root cause chain (probed on parrot): gemma-4's chat template inserts a `<|think|>` token whenever a SYSTEM prompt is present → any request carrying the app persona triggered a hidden reasoning monologue (269-376 output tokens = 5-23s turns); bare prompts never thought, which is why CLI probes looked fine. s2s already sends a no-thinking flag but in the vLLM/llama-server dialect (`chat_template_kwargs.enable_thinking=false`), which Ollama silently ignores; Ollama's dialect is `reasoning: {effort: "none"}` (verified: persona prompt answered in 4 tokens / 1.3s through the tunnel). ### Local LLM setups tested

- [15.07.2026] **Local stack PoC verdict + three-tier backend plan**: full local chain (desktop app → sim daemon → app in local connection mode → all-MLX s2s on :8765) works end-to-end but is PoC-grade — weaker conversation quality than the hosted backend and an occasional monotone-tone TTS bug in the sim. Decision: hosted backend = primary, on-device = fallback/dev, and a third tier to explore: LLM on Imperial's GPU cluster via SSH tunnel with s2s's responses-api backend — STT/TTS stay on the Mac so participant audio never leaves the room, only text goes to university infrastructure.
- [14.07.2026] **llama-server + gemma-4-E4B Q4 (5.0GB) via s2s responses-api**: worked, but 23 t/s and memory pressure on the 16GB Air → intermittent PortAudio -9986 crashes at audio-stream open.
- [14.07.2026] **llama-server + gemma-4-E2B QAT q4_0 (3.35GB, ctx 8192)**: LLM solved — 43-48 t/s, 0.7-1.7s/turn, no more -9986. New bottleneck: Qwen3-TTS first-audio erratic (1.5-14s), suspected llama.cpp↔MLX Metal contention; end-to-end 6-26s/turn.
- [14.07.2026] **All-MLX consolidation, first attempt (invalid test)**: `--local_mac_optimal_settings` alone doesn't forward `--model_name` to the MLX handler (parser binds it by pre-parsing `--llm_backend`, which the preset sets too late) → silently loaded default Qwen3-4B bf16 (8GB) → swap, thermal throttling, Metal OOM. Lesson: always pass `--llm_backend mlx-lm` explicitly and verify the loaded model name in the startup log.
- [15.07.2026] **All-MLX, corrected** (`--llm_backend mlx-lm --model_name mlx-community/gemma-4-e2b-it-4bit`, 3.55GB): **VERIFIED — the chosen local stack.** 1.3–3.3s speech-to-speech per turn, TTS first-audio constant ~0.3s, TTS RTF ~1.4 (faster than realtime) — confirms the Metal-contention diagnosis; llama-server retired. Prerequisite: s2s pins mlx-lm==0.31.1, which predates the gemma4 architecture → patch the uv tool venv with `uv pip install --python ~/.local/share/uv/tools/speech-to-speech/bin/python "mlx-lm==0.31.3"` (any later `uv tool install/upgrade speech-to-speech` silently reverts this).
- [15.07.2026] **Answer brevity is prompt, not model**: s2s's default `--init_chat_prompt` caps responses at "less than 20 words"; overriding it produced solid multi-sentence answers from the 2B model (incl. context-carrying follow-ups) at 1.7–2.8s/turn. In production the app's persona instructions replace this default, so only standalone testing is affected.
- [15.07.2026] **Turn-taking limits of the s2s engine (standalone `--mode local`)**: silence-based endpointing (`--live_transcription_min_silence_ms`, default 500ms; raised to 900ms) still clips hesitant/pausing speakers — relevant to the study whichever backend is used, since the hosted backend runs the same engine. Separately, observed a likely engine bug: turns reopened 13s after being answered (outside both `--speculative_reopen_ms 2500` and the 7s unanswered cap), gluing new speech onto old turns and re-answering them. Not tunable; decision: stop tuning standalone mode, evaluate turn-taking on the real path (server mode + app over realtime websocket) and report upstream if it reproduces there.
